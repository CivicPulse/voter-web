    **Step 3 — Mapping function (src/lib/election-capabilities.ts):**
    Create a new file with the pure mapping function and EMPTY_FLAGS constant:

    ```typescript
    import type { CapabilitiesResponse, ElectionFeatureFlags } from "@/types/elections"

    export const EMPTY_FLAGS: ElectionFeatureFlags = {
      search: false,
      raceCategory: false,
      geographic: false,
      electionDate: false,
      filterOptions: false,
    }

    export function mapCapabilitiesToFlags(
      response: CapabilitiesResponse,
    ): ElectionFeatureFlags {
      const params = new Set(response.supported_filters)
      return {
        search: params.has("q"),
        raceCategory: params.has("race_category"),
        geographic: params.has("county") || params.has("district"),
        electionDate: params.has("election_date"),
        filterOptions: response.endpoints?.filter_options ?? false,
      }
    }
    ```

    **Step 4 — Hook (src/lib/hooks/use-election-capabilities.ts):**
    Create the TanStack Query hook following the useApiCapabilities/useUserRole pattern:

    ```typescript
    import { useQuery } from "@tanstack/react-query"
    import { getElectionCapabilities } from "@/lib/api/elections"
    import { mapCapabilitiesToFlags, EMPTY_FLAGS } from "@/lib/election-capabilities"
    import type { ElectionFeatureFlags } from "@/types/elections"

    export function useElectionCapabilities(): ElectionFeatureFlags & { isLoading: boolean } {
      const { data, isPending } = useQuery({
        queryKey: ["election-capabilities"],
        queryFn: async () => {
          const response = await getElectionCapabilities()
          return mapCapabilitiesToFlags(response)
        },
        staleTime: 5 * 60 * 1000,    // 5 minutes
        gcTime: 10 * 60 * 1000,      // 10 minutes
        retry: 1,                    // 1 retry, then treat as unavailable
      })

      return {
        ...(data ?? EMPTY_FLAGS),
        isLoading: isPending,
      }
    }
    ```

    Key details per user decisions:
    - Use `publicApi` (via getElectionCapabilities) — no auth redirect on 401
    - Strict fallback: `data ?? EMPTY_FLAGS` — if query errors, all flags false
    - Do NOT use `placeholderData` or `keepPreviousData` — strict fallback means stale cache is NOT preserved
    - Global scope — no `enabled` guard, always fetches (no auth dependency)
    - `retry: 1` — one retry on failure, then give up

    Create a comprehensive API specification document at `.planning/API-SPEC.md` that the backend team can implement without follow-up questions. The document should cover:

    **Structure:**
    1. **Overview** — Purpose of the spec, relationship to existing elections API
    2. **Capabilities Endpoint** — `GET /elections/capabilities`
       - Response shape: `{ supported_filters: string[], endpoints: { filter_options: boolean } }`
       - No authentication required (public endpoint)
       - Returns 200 with current capabilities
       - Example response showing all filters supported
       - Example response showing partial support
       - Versioning note: add new filter names to supported_filters as they're implemented
    3. **New Filter Parameters on GET /elections** — For each parameter:
       - `q` (text search): type string, searches election name and district fields, case-insensitive partial match, minimum 2 characters. Cross-reference: the existing `q` param on `GET /elections/{id}/participation` searches voter names — this `q` searches election records, different domain same convention.
       - `race_category`: type string enum, filters by level of government. Describe the need ("filter by federal, state senate, state house, local") but note the backend team should define the actual enum values and how elections are categorized. Suggest adding a `race_category` field to the Election model.
       - `county`: type string, filters elections by county name (case-insensitive). Propose this filters elections whose district is associated with a given county.
       - `district`: type string, filters elections by exact district name match (case-insensitive).
       - `election_date`: type string (YYYY-MM-DD format), filters to elections on a specific date (exact match, unlike the existing date_from/date_to range filters).
    4. **Filter Options Endpoint** — `GET /elections/filter-options`
       - Returns valid values for each supported filter parameter
       - Response shape: `{ race_categories: string[], counties: string[], election_dates: string[] }`
       - Values should reflect only options that yield results (no dead-end selections)
       - Optional query params to scope options (e.g., pass current filters to get options that are valid given those filters)
       - No authentication required
    5. **Implementation Notes**
       - FastAPI ignores unknown query params by default — existing clients won't break
       - Each parameter can be implemented independently and added to capabilities
       - Suggested implementation order: q (simplest), election_date, race_category, county/district, filter-options (most complex)

    **For each parameter, include:**
    - Parameter name, type, validation rules
    - Behavior description (how it filters)
    - Example request with the parameter
    - Example response
    - Edge cases (empty value, invalid value, no matches)
    - Interaction with existing filters (AND logic — all filters combine)

    **Format requirements per user decision:**
    - Full contracts, not just param lists
    - Type, validation rules, behavior description, example request/response, edge cases for each
    - Race category: describe the need, let backend define enum values
    - Geographic params: propose `county` and `district` as separate params (matches existing data model)
